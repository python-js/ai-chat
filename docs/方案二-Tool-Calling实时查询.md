# 方案二：Tool Calling 实时查询

> 让 LLM 拥有"查询 MySQL"的工具能力，用户提问时由 LLM 判断意图并实时执行 SQL，返回精确结果。

---

## 一、方案概述

利用大模型的 **Function Calling（工具调用）** 能力，给 LLM 注册若干"查询工具"（如查订单、查员工）。用户提问后，LLM 自主判断是否需要调用工具、调用哪个、传什么参数，实时查询 MySQL 并基于结果组织自然语言回答。

**本质**：LLM 作为"智能路由器"，把自然语言翻译成结构化查询。

---

## 二、适用场景

✅ 适合：
- 数据是**结构化记录**（订单、员工、库存、工单）
- 用户问法是**精确查询型**（"查订单 12345 的状态"、"张三的工号"）
- 要求**实时**数据，不能有同步延迟

❌ 不适合：
- 开放式的语义问答（"我们的产品有什么优势"）→ 用方案一
- 需要跨多表复杂关联分析 → LLM 生成 SQL 出错率高
- 对答案准确性零容忍的财务/审计场景

---

## 三、架构设计

```
用户提问："订单 12345 到哪了？"
      │
      ▼
LLM（qwen-plus）分析意图
      │  决定调用工具 query_order({ orderId: "12345" })
      ▼
后端工具函数（预定义、参数化 SQL）
      │  SELECT status, logistics FROM orders WHERE order_id = ?
      ▼
公司 MySQL（只读账号）
      │  返回 { status: "已发货", logistics: "SF123..." }
      ▼
LLM 组织自然语言回答
      │
      ▼
"您的订单 12345 已发货，顺丰单号 SF123..."
```

---

## 四、实现步骤（概要）

> 以下为结构设计，具体代码待方案确认后实施。

### 1. 安装依赖
```
npm install mysql2 zod
```

### 2. 新建 MySQL 连接单例 `lib/mysql.ts`
- **必须使用只读账号**（`GRANT SELECT`）
- 连接池保守配置

### 3. 定义工具 `lib/tools.ts`
用 AI SDK 的 `tool()` + zod 定义参数结构，**每个工具对应一个预定义 SQL**：
```
query_order   → 按订单号查订单
query_employee → 按姓名/工号查员工
...
```
**关键**：SQL 是预先写死的模板，LLM 只能填参数（走 `?` 占位符），**绝不能让 LLM 自由拼 SQL**。

### 4. 改造聊天 API `app/api/chat/route.ts`
```
streamText({
  model: llm,
  system: ...,
  messages,
  tools: { query_order, query_employee },  // 注册工具
  maxSteps: 3,                              // 允许"调用→拿结果→总结"多轮
})
```

### 5. ⚠️ 前端必须改造
当前前端用的是 `TextStreamChatTransport`（纯文本流），**不支持工具调用协议**。
必须切换为 `DefaultChatTransport`（数据流协议），并调整 `useChat` 的消息渲染逻辑。

## 五、风险与局限（必读）

### 安全风险（最高优先级）
- **SQL 注入 / 越权**：如果让 LLM 自由生成 SQL，可能被诱导执行 `DROP TABLE` 或读取越权数据。
- **防护措施（缺一不可）**：
  1. 只读数据库账号（物理层面杜绝写操作）
  2. 预定义 SQL 模板 + 参数化查询（LLM 只填参数）
  3. 工具白名单（只暴露允许的表和操作）
  4. 参数用 zod 严格校验类型和范围

### LLM 判断不稳定
- LLM 可能**调错工具**、**填错参数**、或**该调用时不调用**。
- 例：用户说"查一下那个订单"，没说单号，LLM 可能瞎编一个参数。
- **缓解**：工具描述写清楚；参数缺失时让 LLM 反问用户。

### 性能与成本
- 一次问答可能触发多轮 LLM 调用（判断 → 调用 → 总结），**延迟和 token 成本都高于纯 RAG**。
- 免费额度消耗更快。

### 前端改造成本
- 必须从 `TextStreamChatTransport` 迁移到 `DefaultChatTransport`。
- 消息渲染需要处理 tool-call 类型的 part，现有代码要调整。

### 复杂查询能力有限
- 多表 JOIN、聚合统计（"这个月销售额多少"）LLM 容易出错。
- 这类需求建议做成固定的报表工具，而非交给 LLM。

---

## 六、边界条件

| 场景 | 表现 |
|------|------|
| 单表精确查询（按主键/单号） | 效果好，推荐 |
| 2 表以内简单关联 | 可用，需充分测试 |
| 复杂多表聚合分析 | 不推荐，出错率高 |
| 用户表述模糊（缺关键参数） | 依赖 LLM 反问能力，体验不稳定 |
| MySQL 不可用 | 工具调用失败，LLM 会告知用户查询失败 |

## 七、改动清单

| 文件 | 操作 | 说明 |
|------|------|------|
| `lib/mysql.ts` | 新增 | MySQL 只读连接单例 |

| `.env` | 修改 | 增加 MYSQL_* 配置 |

**涉及前后端联动改造，工作量明显大于方案一。**

---

## 八、与方案一的关系

- 本方案适合**精确查询**，方案一适合**语义问答**，两者互补。
- 建议：**先落地方案一**（改动小、见效快），验证有精确查询需求后再叠加方案二。
- 两个方案共用同一个 `lib/mysql.ts` 连接层，不重复建设。
