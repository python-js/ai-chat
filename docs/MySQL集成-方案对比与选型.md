# MySQL 数据集成方案对比与选型

> 目标：让智能客服能够利用公司现有 MySQL 数据库中的数据回答问题。
> 本文档对比两种可行方案，帮助做出选型决策。

---

## 一、背景与约束

- 现有系统：Next.js 全栈 + PostgreSQL（pgvector）+ 百炼大模型（qwen-plus + text-embedding-v3）
- 现有 RAG 链路：文档上传 → 分块 → embedding → pgvector → 相似度检索 → LLM 回答
- MySQL 定位：**只读数据源**（不写入、不修改公司业务库）

**核心约束**：pgvector 是 PostgreSQL 独有扩展，MySQL 无法替代 PostgreSQL 承担向量检索职责。因此 MySQL 只能作为**数据来源**，不能替代现有向量库。

---

## 二、两种方案概览

| 维度 | 方案一：RAG 知识同步 | 方案二：Tool Calling 实时查询 |
|------|---------------------|------------------------------|
| **核心思路** | 把 MySQL 数据同步成向量，复用现有检索链路 | 让 LLM 实时调用工具查询 MySQL |
| **数据时效** | 有延迟（取决于同步周期） | 实时 |
| **适合的数据** | 文档型、说明型（产品资料、FAQ、制度） | 结构化、精确型（订单、员工、库存） |
| **适合的问法** | "这个产品的保修政策是什么？" | "帮我查订单 12345 的状态" |
| **改动范围** | 小（新增同步脚本，复用现有 RAG） | 大（需改前端传输协议 + 后端工具链） |
| **安全风险** | 低（数据已脱敏入库） | 高（LLM 生成 SQL，需严格防护） |
| **实现成本** | 低 | 中高 |

---

## 三、决策指南

```
你的 MySQL 数据是什么类型？
│
├─ 文档/说明/FAQ 类（适合语义检索）
│     → 选方案一（RAG 知识同步）
│
├─ 结构化记录（订单/员工/库存，需精确查询）
│     → 选方案二（Tool Calling 实时查询）
│
└─ 两者都有
      → 分阶段：先方案一打通，再按需叠加方案二
      （两个方案不冲突，可以共存）
```

**关键判断问题**：
- 用户会问"查某个具体记录"吗？→ 是 → 方案二
- 用户会问"某某政策/原理/怎么做"吗？→ 是 → 方案一

---

## 四、共同前置工作（两个方案都需要）

1. 安装 MySQL 驱动：`npm install mysql2`
2. 新建 `lib/mysql.ts` 连接单例（参考 `lib/prisma.ts` 的单例模式）
3. 使用**只读数据库账号**连接（`GRANT SELECT ON ...`），从源头杜绝写操作
4. 在 `.env` 中配置 MySQL 连接信息（不要硬编码）

## 六、通用风险提示

无论选择哪个方案，都必须注意：

1. **网络连通性**：本地开发机能否访问公司 MySQL（可能需要 VPN / 内网穿透）
2. **数据权限**：确认你有权读取目标表的数据，涉及敏感数据（薪资、客户隐私）需审批
3. **连接数限制**：MySQL 有最大连接数限制，应用连接池配置要保守
4. **字符编码**：确认 MySQL 是 utf8mb4，避免中文乱码
